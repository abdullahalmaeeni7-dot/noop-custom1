# Direct tracker-history download

The earlier connection was a live-HR subscriber. It did not request stored tracker records. This addition introduces a user-triggered **Tracker → Download from tracker** read transfer, alongside live receipt recording. It requires a successful custom-service handshake, all required notifications and writes with response; a generic Bluetooth Heart Rate Service connection alone does not qualify.

The narrow command surface adds `SEND_HISTORICAL_DATA` (0x16) and `HISTORICAL_DATA_RESULT` (0x17). No force-trim, erase, firmware, clock-setting or bond-reset commands are exposed. History End metadata supplies an expected packet count and an eight-byte cursor token. The app counts complete CRC-validated historical records and history sideband types 0x34–0x37; live data and metadata are excluded. An incomplete marker, unknown frame-envelope revision, count mismatch, buffer overflow or transport failure prevents acknowledgement. Buffers are bounded to 20,000 packets and 8 MiB per batch.

A complete batch, including every unrecognized body, is stored losslessly in `Documents/whoop-device-history`. Atomic writes are synchronized before an opaque saved receipt is issued. The transfer requires that receipt to match the exact pending frames, token and end marker before producing an ACK. A duplicate cursor with different bytes cannot overwrite the saved batch. Replays repair/reuse the same raw file, not duplicate records. A band may release a batch after acknowledgement, so retain the raw ZIP as a separate backup.

Known physiological projections are deliberately narrow: gen4 R12/R24 bodies of at least 89 bytes, and gen5 R18 bodies of at least 112 bytes. They supply device timestamps, a range-checked heart-rate byte, and up to four plausible R-R intervals. All other bytes remain raw, including optical/IMU formats not projected here. SpO2 percentages, skin temperature, sleep stages, HRV, Strain and Recovery are not invented from unknown bytes. Device timestamps use the previously recovered Unix-seconds / 32768-ticks clock; pre-2000 or more-than-five-minutes-future timestamps stay in the archive without entering the chart. No receipt-time substitution or clock write corrects them silently.

The dashboard stores one genuine historical HR sample per minute as a trace preview. Original provider scores and the selected calendar day are preserved. The complete raw archive is independent of the existing bounded dashboard JSON. A chart-index failure is surfaced and does not discard a complete raw batch or interrupt otherwise durable raw transfer. The raw ZIP export streams every saved history file and includes a CSV of supported decoded HR/R-R records with their original device timestamps, batch tokens and clock-plausibility flags; it is a separate device-data format, not an official WHOOP export and not the JSON app backup. Unknown packets can be decoded later from those original bytes.

Home and camera overlays now default to supplied WHOOP scores. Local Strain estimates remain explicitly opt-in in tracker settings. HR/R-R records are measurements; local derived values must not be presented as official WHOOP Recovery, Sleep or Strain. Official score sync still requires the configured account flow or supported provider exports.

## Evidence and license

The new field and transfer reference is the [MIT-licensed OpenStrap protocol snapshot](https://github.com/OpenStrap/protocol/tree/3ecf17e89ae2750ee0a64155266b41a9a3aa9091), with [the complete MIT notice](ThirdParty/OpenStrap-protocol-MIT-LICENSE.txt). Later AGPL code is not incorporated. Three captured reference records are retained in `Tests/WHOOPCoreTests/Fixtures/WhoopCapturedHistory.json`: two gen4 records and one full gen5 R18 frame. Gen4 framing and control-case fixtures are independently generated using Python zlib and bitwise reference CRCs. They are public reference captures, not this user's band traffic. Earlier Android static header/time evidence remains documented in DEVICE-HISTORY.md and DEVICE-TIME.md.

Tests verify captured HR/R-R/timestamps and fragmentation; byte-exact request/ACK frames; required saved receipts; failed disk writes; idempotent replays; conflicting cursors; raw ZIP preservation; unknown record retention; incomplete count/marker rejection; unsupported frame revisions; and bounded buffers. Apple compilation and physical transfer must be recorded separately. This work does not establish firmware compatibility or completed transfers on the user's physical band, nor full official-app parity.

Current portable verification: all 183 Swift tests passed; app Swift parsing and the 34-source project validator passed. Apple SDK compilation and a physical-band transfer are separate pending checks.
